## 1. AKShare 预计算指标年报过滤缺失

> 已收录为 [incident 004](incidents/004-data-accuracy-20260604.md) P0

### 背景

项目用 AKShare 拉取 A 股财务数据，`stock_financial_analysis_indicator` 接口返回预计算指标（存货周转率、应收账款周转率等），与自拉三大报表拼接后传入计算模块。

### 问题

用茅台 (600519) 与新浪财经/东方财富交叉验证时，发现存货周转率严重偏离：本项目 2021 年 = 0.08 次，权威源 = 0.289 次。

### 排查

1. 打印 indicators DataFrame，发现返回 25 行（5 年 × 5 个报告期：Q1/Q2/Q3/Q4/年报）
2. 三大报表的 `fetch_balance_sheet` 等方法有 `_filter_annual()` 过滤年报（报告日以 `1231` 结尾），但 `fetch_indicators` **没有过滤**，直接返回全部 25 行
3. `calc_efficiency` 用 `indicators.iloc[i]` 按索引取值，前 5 行全是 2020 年的季度数据，导致所有年份取到错误的指标值

### 方案

`akshare_client.py` 的 `fetch_indicators` 增加年报过滤：

```python
mask = df["日期"].astype(str).str.endswith("12-31")
df = df[mask].reset_index(drop=True)
```

### 结果

存货周转率从错误的 0.08 修正为 0.274，与新浪财经 0.289 基本一致（微小差异来自底层取数时间点不同）。

### 面试话术

> 财务数据 API 返回的粒度不一定是年报，可能是季报+年报混合。我在交叉验证阶段发现数据异常，追溯到数据拉取层缺少年报过滤。修复后用茅台与新浪财经对比，6 个核心指标完全一致。

## 2. AKShare 预计算字段缺失 - 应收账款周转率

> 已收录为 [incident 011](incidents/011-akshare-ar-turnover-nan-20260604.md)

### 背景

应收账款周转率原设计从 AKShare `indicators` 的 `应收账款周转率(次)` 字段取值。

### 问题

该字段对所有年份返回 NaN。茅台以直销为主，应收账款极少（几百万 vs 千亿级收入），AKShare 未计算此指标。

### 方案

改为自算：`营业收入 / 应收账款平均余额`（年初+年末均值）。最老年份无上年数据时退化为单年值。

### 结果

- 茅台 2024 应收账款周转率 ~4,308 次（应收极少属正常）
- 新增 3 个单元测试覆盖（当年/上年均值/最老年份退化）
- 全量 140 测试通过

### 面试话术

> 外部数据源的字段不一定完整，特别是对特殊公司（如茅台应收极少）。我做了降级方案：AKShare 预计算字段缺失时改用资产负债表自算，并用年初年末均值提升准确性。

## 3. 行业特殊性导致红黄绿灯误判

> 已收录为 [incident 002](incidents/002-report-accuracy-20260526.md)

### 背景

项目用硬编码通用阈值做红黄绿灯评判（如存货周转率 <2 = 红灯），LLM 基于灯色生成分析报告。

### 问题

茅台存货周转率约 0.27 次（红灯），但这是白酒行业的正常经营模式--基酒需陈酿 3-5 年，库存天然偏高。如果 LLM 机械地把红灯解读为"运营效率风险"，会误导用户。

同类问题：银行资产负债率 90%+（正常）、房地产高杠杆（正常）、科技公司轻资产周转率低（正常）。

### 方案

两层解决：

1. **Prompt 层**（已实现）：在基本面分析 prompt 增加行业特殊性引导段落，列出白酒/银行/地产/科技/公用事业 5 个行业的特殊考量，要求 LLM 在解读红灯时区分"行业特性"和"真实风险"
2. **阈值层**（v2.0 规划）：从硬编码改为 `thresholds/{industry}.yaml`，按行业加载不同阈值

### 结果

LLM 生成的报告会在红灯指标旁标注"该指标受行业经营模式影响，不构成实质性风险"，而非机械报风险。

### 面试话术

> 通用财务指标的评判阈值不能一刀切。白酒的存货周转率天然偏低是行业特性不是风险。我在 prompt 层加了行业感知引导，让 LLM 区分行业特性与真实风险。架构上也预留了按行业加载不同阈值的扩展点。

## 4. 简单 ROE vs 加权 ROE 的方法差异

> 已收录为 [incident 004](incidents/004-data-accuracy-20260604.md) P1

### 背景

本项目 ROE 原用 `净利润 / 期末股东权益`，后升级为优先取 AKShare 预计算的加权 ROE，降级时自算用 `归母净利润 / 平均归母权益`。

### 问题

与新浪财经对比，ROE 差异 1-2%（如 2024 年本项目 36.91% vs 新浪 36.02%）。

### 分析

这是计算口径差异：

- 简单 ROE = 归母净利润 / 期末归母权益（分母用期末快照）
- 加权 ROE = 归母净利润 / 加权平均归母权益（考虑年内增发、分红等权益变动）

当前代码优先取 AKShare 的加权 ROE（`加权净资产收益率(%)`），缺失时降级自算。会计准则推荐加权 ROE。

### 面试话术

> 验证时发现 ROE 与权威源有 1-2% 差异。排查后确认是计算口径不同：我们用期末权益，权威源用加权平均权益。这不是 bug，是已知的精度-复杂度权衡。文档里标注了这个差异，v2.0 可以升级为加权算法。

## 5. 指标验证方法论

### 背景

财务分析系统的核心是指标计算的正确性，一个指标算错后面全错。

### 方法

1. 选一只特征鲜明的股票（茅台：高毛利、低负债、大现金）做全量验证
2. 从至少 2 个权威源（新浪财经 + 东方财富）取对比数据
3. 按三类结果归因：
   - **完全一致** -> 信任
   - **方法差异**（期末 vs 平均值、简单 vs 加权）-> 记录，MVP 可接受
   - **真 bug**（年报未过滤、字段缺失）-> 立即修复
4. 输出验证报告，标注每个指标的数据源和差异原因

### 结果

| 类型       | 数量 | 指标                                                              |
| ---------- | ---- | ----------------------------------------------------------------- |
| 完全一致   | 6    | 资产负债率、流动比率、速动比率、毛利率、净利率、经营现金流/净利润 |
| 方法差异   | 3    | ROE、ROA、总资产周转率（期末 vs 平均值）                          |
| 已修复 bug | 2    | 存货周转率（年报过滤）、应收账款周转率（改自算）                  |

> 注：经营现金流/净利润后从「合并净利润」改为「归母净利润」口径（#20），验证结论需以归母口径重新确认。

### 面试话术

> 我用茅台做了全量交叉验证，和新浪财经/东方财富对比。把差异分成三类处理：完全一致的直接信任，方法差异的记录为已知权衡，真 bug 立即修复。最终 6 个核心指标完全一致，2 个 bug 修复，3 个方法差异有文档记录。
